# Hermes vLLM NodePort Policy E2E Test Report

Test date: 2026-05-27

## Summary

This test validated the Hermes CRD policy-triggered build path on EC2 with kind. In this report, `v2` refers to the second test report and the CRD policy trigger path. It does not refer to SOCI index manifest v2; this test still built a SOCI v1 index.

Key findings:

1. The `HermesPolicy` CRD can control which Pod images trigger SOCI index builds.
2. The controller observed a Pod that matched `.*vllm.*` through the Pod watcher and automatically enqueued a build.
3. The worker-side `hermes-daemon` still reached the controller NodePort through `http://127.0.0.1:30080` to fetch the index and zTOCs.
4. The normal overlayfs cold-start path for the vLLM image reached Pod Ready in about 339.197 seconds. The Hermes lazy loading path reached Pod Ready in about 14.706 seconds, a roughly 23.1x improvement.
5. An image that did not match the policy did not produce an artifact, and its Pod still started successfully through the daemon fallback path.

## Method

The test had three phases:

1. `hermes-vllm-policy-v2-overlay`: Hermes daemon was not installed. The vLLM Pod used the default overlayfs path, and the test recorded the normal image pull, unpack, and Pod Ready time.
2. `hermes-vllm-policy-v2`: the test deployed the `HermesPolicy` CRD, RBAC, controller, and NodePort backing object. The daemon still used `127.0.0.1:30080` as its actual endpoint. A deliberately Pending `hermes-policy-trigger` Pod was created only to make the controller watcher observe the vLLM image and trigger the build. This avoided having the worker pull the full vLLM image before the lazy loading measurement.
3. After the index became Ready, `hermes-daemon` was installed on the worker node and containerd was switched to the `soci` snapshotter. The test then started the real vLLM Pod. After that, it started a busybox Pod that did not match the policy to verify that images without built artifacts still fall back and run normally.

## Interpretation

This test proves that the CRD policy trigger path works. A user can create a `HermesPolicy`, and the controller can automatically decide whether to build a SOCI index based on Pod images. The node-side path still only needs local `127.0.0.1:30080` access to the controller through NodePort.

Hermes still does not remove the first index build cost. In this run, the vLLM image took about 9 min 26.9 sec from policy trigger to index Ready. The image pull portion took about 2 min 3 sec, and the remaining time was mainly zTOC/index construction.

The benefit appears on the application Pod startup path after the artifact is Ready. For the same vLLM image, the normal overlayfs cold-start path took about 5 min 39 sec, while the Hermes lazy loading path took about 14.7 sec.

Images that do not match policy do not enter the controller artifact store. With `fallback_to_registry=true`, the `soci` snapshotter falls back to the container runtime when no Hermes index exists. That means a narrow policy scope does not block non-target images.

## Notes

The `hermes-policy-trigger` Pod was intentionally kept Pending. It was used only to trigger the controller watcher, not as a workload. This avoids polluting the lazy loading test by letting the worker pull the full vLLM image during the trigger phase.

The controller currently enqueues the same tag again on Pod update events. Because the image digest is already Ready, those later paths quickly hit the cache and skip the actual rebuild. The logs can still show several fast pull/resolve operations. A later optimization could add stronger deduplication by Pod UID/resourceVersion or image tag to reduce unnecessary resolves.

The negative test used busybox to isolate the policy miss and daemon fallback behavior. The main performance test still used the large vLLM image.
